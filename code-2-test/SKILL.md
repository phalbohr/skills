# Test Writing Conventions

## 1. Core Validity Contract

Tests MUST verify real behavior and MUST fail when production code is broken.

- Every test asserts a meaningful outcome — not just that code runs without throwing
- If production code logic is deleted or inverted, the test MUST turn red — a test that passes on broken code is worse than no test
- Do NOT write tests that only inflate coverage metrics (e.g., calling a method and asserting nothing, or asserting `assertNotNull(result)` as the sole check)
- **Unit tests:** mock only external dependencies (DB, HTTP, time) — never mock the class/function under test itself
- **Integration tests:** mock only out-of-process external systems (third-party APIs, email) — internal layers run real code

## 2. Testing Approach

Test through the PUBLIC contract ONLY. Do NOT use reflection to access private fields/methods unless absolutely impossible otherwise (last resort).

## 3. Arrange-Act-Assert (AAA)

Structure tests strictly into Arrange, Act, and Assert blocks separated by a SINGLE blank line.
**CRITICAL:** ZERO comments to label these sections — no `// Given`, `// When`, `// Then`, `// Arrange`, `// Act`, `// Assert`, or any equivalent.

```java
// CORRECT
@Test
void shouldReturnProduct_whenIdExists() {
    var product = new Product(1L, "Widget");
    when(repository.findById(1L)).thenReturn(Optional.of(product));

    var result = service.getById(1L);

    assertThat(result).isEqualTo(product);
}

// WRONG — section comments are forbidden
@Test
void shouldReturnProduct_whenIdExists() {
    // Arrange
    var product = new Product(1L, "Widget");
    // Act
    var result = service.getById(1L);
    // Assert
    assertThat(result).isEqualTo(product);
}
```

## 4. Test Redundancy & Coverage

Minimize duplicate tests without losing coverage (lines, branches, statements).

- Merge duplicate scenarios using `@ParameterizedTest`
- Remove tests that provide ZERO unique coverage EXCEPT those documenting a specific bug regression or compliance requirement

## 5. Splitting Large Test Classes

If a test class exceeds **500 lines**, split it by public method under test:

- Create directory `[classname]/` (lowercase class name)
- Name classes `[ClassName][MethodName]Test.java`

Example: `ProductServiceTest` at 600 lines → `productservice/ProductServiceGetByIdTest.java`, `productservice/ProductServiceCreateTest.java`

## 6. Refactoring for Testability

If production code is hard to test (SRP violations, deep nesting, unclear entry points), **propose refactoring to the user** before writing complex brittle tests to work around bad design.

## 7. Integration Test Naming

Integration tests MUST end with `IT` or `IntegrationTest` (e.g., `MassStockControllerIT`).
Do NOT use `Test` suffix for integration tests — Gradle configuration uses naming to separate unit from integration test execution.

| Type | Suffix | Example |
|---|---|---|
| Unit | `Test` | `ProductServiceTest` |
| Integration | `IT` or `IntegrationTest` | `ProductControllerIT` |

## 8. Never Test Lombok-Generated Code

**NEVER** write tests for `equals`, `hashCode`, `toString`, getters, setters, or constructors generated by Lombok (`@EqualsAndHashCode`, `@Data`, `@AllArgsConstructor`, etc.).

This is an antipattern — you test the library, not business logic. JaCoCo excludes this code automatically via `lombok.config` (`addLombokGeneratedAnnotation=true`). If JPA identity correctness matters, verify it implicitly through integration tests that use the repository.

## 9. Mockito `lenient()` — Use Only When Justified

**Default: strict stubs.** `@ExtendWith(MockitoExtension.class)` enables `STRICT_STUBS` — any stub set up but never called fails with `UnnecessaryStubbingException`. This catches dead test setup and reveals unnecessary dependencies.

**Use `lenient()` only in these cases:**

1. **`@BeforeEach` shared stubs** — stub applies to all tests but is only exercised in some (e.g., a `findById` that every test needs except the "not found" case)
2. **Parameterized tests** — not every iteration takes every branch; some stubs unused in certain parameter combinations
3. **Conditional code paths** — production code uses short-circuit evaluation (`||`, early `return`), so a stub on a later branch is skipped when an earlier branch triggers
4. **Temporary during TDD** — while writing a test before all stubs are wired up; remove `lenient()` once the test is complete

**Do NOT use `lenient()` to silence Mockito on stubs that ARE always called** — that hides bugs. If production code ever stops calling a dependency (e.g., someone removes `repository.findById()`), strict mode catches it immediately; `lenient()` lets the test pass silently on broken code.

**Practical rule:** before reaching for `lenient()`, ask — _can this stub ever NOT be called in this test?_ If no → use `when()`. If yes → `lenient()` is justified.
